\section{Introduction}

Verifying that hardware and software systems behave correctly under all possible inputs is a fundamental challenge in computer science. Traditional testing approaches require engineers to enumerate concrete inputs by hand, which makes it difficult to achieve complete coverage of all possible behaviors. Formal verification methods address this limitation by reasoning about all inputs simultaneously, but they often require significant manual effort to apply.

This paper presents a symbolic execution engine for transition systems described in the BTOR2 format, a word-level model checking language widely used for hardware verification. Rather than running a system on one concrete input at a time, our engine keeps inputs symbolic and explores all feasible execution paths in parallel, using an SMT solver to determine which branches are reachable and to detect violations of safety properties. When a bad state is reachable, the engine reports both the symbolic expression that was violated and the path condition that witnesses the violation.

\subsection{Symbolic Execution}

Symbolic execution is a way of executing a program abstractly, such that on abstract execution covers multiple possible inputs of the program that share a particular execution path through the code \cite{aldrich2018symbolic}. Each input of symbolicly executed code is represented as a symbol rather than assigning it a concrete value. When the value is referenced such as for an if statement, the execution path branches, where one path the symbolic value is evaluated as true while the other path the symboilic value is evaluated as false.

\subsubsection{Symbolic Execution in Industry}

One of the key uses for symbolic execution is in testing. Most unit tests, require the programmer to hardcode in values to test, resulting in various unit tests to cover all branches the code can tranverse. On the other hand, a symbolic execution would execute simutaneously for all possible inputs. Algorithm~\ref{alg:simple-example} gives the following example.

\begin{algorithm}
    \caption{Algorithm 1}
    \label{alg:simple-example}
    \begin{algorithmic}[1]
    \Require $x, y \in \mathbb{Z}$
    \State $a \gets x + y$
    \If{$a \bmod 2 = 0$}
        \State \Return error ``$a$ is even''
    \Else
        \State \Return $a$
    \EndIf
    \end{algorithmic}
\end{algorithm}
    
With a glance, we can see that using any combination of numbers such that their sum results in an even number will result in an error. There is no way to cover all cases of failure using unit tests, as there are an infinite number of way which we can stumble onto this error. Instead of testing with unit tests such as $x=1, y=1$, symbolic execution represents the inputs as symbols $x=x_0, y= y_0$. Consider a symbolic execution of the algorithm above; Figure~\ref{fig:symbolic-trace} shows how we start with representing each input symbolically.

Following the execution, we translate every instance of $x$ with $x_0$ with the same case for $y$. Where it gets interesting is when the the execution has a branching path. In the if statement, because a is symbolic, the executor cannot evaluate the condition concretely. Instead, execution forks into two paths, each assuming a different outcome of the condition and adding the corresponding constraint to the path condition. Our symbolic execution analysis shows us that there are two possible families of results: one which results in an error and one in a valid return value. Tracing its path constraint reviews to us that the family of inputs satisfy the constraint $a\bmod 2 == 0$ results in an error. Now imagine a similar example, but with a twist. Prior to running this program with symbolic execution, one can add constraints to the path. Algorithm~\ref{alg:precondition-example} gives an example where we start with a given constraint that $x_0+y_0=1$.

With the constraint, the path condition which leads to the error is contradictory, which shows that the path is impossible and no paths lead to errors. In industry, programmers, can create tests with given preconditions (constraints) and run until the program terminates. Instead of throwing an error, we can use assertion statements as post-conditions. If it terminates without an error, the program is robust across all set of inputs. Otherwise, a symbolicly executed program will return a concrete set of conditions which will give an error or violate a post-condtiion.

\subsubsection{While loops}

A while loop can be viewed as repeated conditional branching. At each iteration, the loop condition is evaluated, and execution either continues into the loop body or exits the loop. In this sense, a while loop behaves like an if statement that is evaluated repeatedly, where each evaluation produces a new branch in the execution path. Because symbolic execution already handles branching through constructs such as if statements, loops can be handled in a variety of ways. In imperative symbolic execution engines, loops are typically handled directly by repeatedly exploring these branches. In declarative or functional settings, another common approach is to represent the loop by unrolling it into a recursive function. This removes the explicit loop construct while preserving the same branching behavior. For illustration, see Algorithm~\ref{alg:count-ones-while}.

\begin{algorithm}
    \caption{Count Number of 1's in a Bit Vector}
    \label{alg:count-ones-while}
    \begin{algorithmic}[1]
    \Require $v$ is a bit vector of length $n$
    \State $count \gets 0$
    \State $i \gets 0$
    \While{$i < n$}
        \If{$v[i] == 1$}
            \State $count \gets count + 1$
        \EndIf
        \State $i \gets i + 1$
    \EndWhile
    \State \Return $count$
    \end{algorithmic}
\end{algorithm}

\begin{algorithm}
    \caption{Recursively Count Number of 1's in a Bit Vector}
    \label{alg:recursive-count-ones}
    \begin{algorithmic}[1]
    \Require $v$ is a bit vector of length $n$
    \Function{count\_ones}{$v, i, n$}
        \If{$i == n$}
            \State \Return $0$
        \ElsIf{$v[i] == 1$}
            \State \Return $1 +$ \Call{count\_ones}{$v, i+1, n$}
        \Else
            \State \Return \Call{count\_ones}{$v, i+1, n$}
        \EndIf
    \EndFunction
    \State \Return \Call{count\_ones}{$v, 0, n$}
    \end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:recursive-count-ones} rewrites it as a recursive function. In practice, splitting branches continous may lead to state explosion, where thousands of branches consume memory within iterations. To combat this, programmers either set a recursion limit, terminating the branch which gets stuck, or find a different way to represent the while loop, using the loop invariant. Figure~\ref{fig:recursive-execution-tree} shows a tree of the branching paths created from a symbolic execution of Algorithm~\ref{alg:recursive-count-ones}.

\subsection{BTOR2}

BTOR2 is a word-level model checking format for capturing models of hardware and potentially software in a bit-precise manner. The exact architecture in which it is defined can be found at \cite{niemetz2018btor2}.

For the purposes of this project, we parse the language into a \emph{transition system}, formalized as a tuple $(\mathcal{S},\,\mathcal{I},\,\mathit{init},\,\mathit{next},\,\mathcal{C},\,\mathcal{B})$:
\begin{itemize}
    \item $\mathcal{S}$: the set of state variables;
    \item $\mathcal{I}$: the set of free (input) variables;
    \item $\mathit{init}$: for each $s \in \mathcal{S}$, the initial value $\mathit{init}(s)$;
    \item $\mathit{next}$: for each state variable $s \in \mathcal{S}$, the next-state function $\mathit{next}(s,\,\mathcal{I})$ giving the value of $s$ after one step as a function of the current state and chosen inputs;
    \item $\mathcal{C}$: the set of constraints that every chosen input must satisfy at each step; and
    \item $\mathcal{B}$: the bad-state predicate; the system is unsafe if some execution reaches a state satisfying $\mathcal{B}$.
\end{itemize}
These components map directly to BTOR2: \texttt{state} (with \texttt{init} and \texttt{next}), \texttt{input}, \texttt{constraint}, and \texttt{bad}.

The BTOR interpreter runs the transition system step by step: it initializes each state variable using $\mathit{init}$, then at each step chooses concrete values for the inputs in $\mathcal{I}$ that satisfy the constraints in $\mathcal{C}$, evaluates each next-state function in $\mathit{next}$, and updates the state accordingly. After each step, it checks whether the resulting state satisfies the bad-state predicate $\mathcal{B}$.

Consider a system with one state variable $s$ (initialized to $0$, $\mathit{next}(s) = s + \mathit{inp}$), one free input $\mathit{inp}$ constrained by $\mathit{inp} \geq 1$, and bad state $\mathcal{B} \equiv s \geq 3$. Table~\ref{fig:btor2-trace} shows a concrete two-step run that reaches a bad state.

\subsection{SMT Solver}

One of the key challenges of implementing symbolic execution is being able to distinguish whether or not a path is feasible or not. How should a symbolic executor tell whether or not a path is feasible such as in Figure~\ref{fig:symbolic-trace-with-constraint} row 4 or infeasible, like in Figure~\ref{fig:symbolic-trace-with-constraint} row 3.

As always in computer science, one of the best ways to model something is to make it someone else's problem: take an existing solution to a hard problem and leverage it to solve your own. Here, we leverage a SAT solver to determine path feasibility. The remaining challenge is translating each branching condition into a series of boolean equations. This is the role of an SMT (Satisfiability Modulo Theories) solver, which lifts raw SAT solving to richer data types (e.g., integers, bit-vectors). 

One possible way to reduce bit-vector constraints to SAT: model fixed-width integers as bit-vectors (e.g., a 32-bit integer as 32 boolean variables) and encode comparisons as propositional formulas. As a concrete example of such a reduction, consider a 4-bit unsigned integer $x = (x_3, x_2, x_1, x_0)$, where $x_3$ is the most significant bit. One way to encode the condition $x > 4$ is to observe that $4 = (0,1,0,0)_2$ and reason case-by-case over the leading bits: if $x_3 = 1$ then $x \geq 8 > 4$; if $x_3 = 0$ and $x_2 = 1$ then $x \in \{4,\ldots,7\}$, and $x > 4$ requires at least one of $x_1, x_0$ to be $1$; otherwise $x \leq 3$. This yields the propositional formula
\[
    x_3 \;\lor\; \bigl(x_2 \;\land\; (x_1 \lor x_0)\bigr)
\]
which can be passed to a SAT solver. Thus, bit-vector SMT can be lowered to SAT in this way; actual SMT solvers may use different encodings or avoid full bit-blasting.

\subsubsection{Bounded Model Checking}

Rather than implementing a symbolic execution engine, a simpler way of checking program correctness is with Bounded Model Checking(BMC). Here, this verification system translates the program into a system of SMT queries and checks if there exists an example which results in an error.

Using the transition system style from Table~\ref{fig:btor2-trace}, BMC keeps the inputs symbolic and asks whether there exists an assignment within the chosen bound that reaches a bad state. For example, let the initial state be $1$, let $\mathit{next}(s)=s+\mathit{inp}$, and let the bad predicate be $s \geq 4$. Unrolling the system for one step yields Table~\ref{fig:bmc-trace}. The check fails within one step because choosing $i_0 = 3$ gives the next state $1 + i_0 = 4$, which satisfies the bad predicate.

\begin{figure}[H]
    \centering
    \begin{tabular}{|c|c|c|c|c|}
        \hline
        \textbf{step} & \textbf{state} & \textbf{input} & \textbf{next state} & \textbf{bad} \\
        \hline
        Init & $1$ & $i_0$ & $i_0 + 1$ & $-$ \\
        \hline
        1 & $1 + i_0$ & $i_1$ & $i_1 + i_0 + 1$ & yes \\
        \hline
    \end{tabular}
    \caption{One-step bounded model checking trace for the transition system induced by Table~\ref{fig:btor2-trace}. The inputs remain symbolic, and the checker asks whether some assignment, such as $i_0 = 3$, makes the bad predicate true within the bound.}
    \label{fig:bmc-trace}
\end{figure}

This technique is called BMC as it only checks for a finite number of steps. Suppose that the input was constrainted such that $0<i<2$ and that the bad state required the state be $>10$. With a maximum of $9$ steps, BMC would stop after $9$ step concluding that there exists no error.

\section{Implementation}

The high-level goal of our implementation is to perform symbolic execution on BTOR2 transition systems. In this setting, the configuration of the system is the valuation of all its state variables: each state variable holds a value (concrete or symbolic), and two configurations are equivalent if they assign the same value to every state variable. To compute the next step, each configuration is transformed according to the transition function: the next-state expression for each state variable is evaluated, possibly using symbolic inputs, and the result becomes that variable's new value.

Because inputs can be nondeterministic and next-state expressions may contain \texttt{ite} (conditional) branches, a single configuration can lead to multiple successor configurations. We therefore maintain a set of paths, where each path is a pair of (i) a configuration, the current symbolic values of all state variables, and (ii) a path condition: the conjunction of assumptions made to reach that configuration. Given a system and a step bound, we initialize the set of paths, repeatedly apply the transition function to each path's configuration to obtain new paths, and check whether any path reaches a configuration satisfying the bad-state predicate.

\subsection{Step-by-Step Example}

First we illustrate how the symbolic executor runs with an example BTOR2 model. First, the transition system is given by Algorithm~\ref{alg:quiz1}.

\begin{algorithm}
    \caption{Quiz1 transition system}
    \label{alg:quiz1}
    \begin{algorithmic}[1]
    \State \textbf{Input:} \texttt{reset} (1-bit)
    \State \textbf{State:} \texttt{counter} (16-bit), \texttt{\_resetCount} (1-bit)
    \State \textbf{Init:} \texttt{\_resetCount} $\gets 0$
    \State \textbf{Constraint:} $\mathit{implies}(\neg(\mathit{\_resetCount} \geq 1), \mathit{reset})$
    \State \textbf{Bad:} $\neg\mathit{reset} \land (\mathit{counter} > 1)$
    \State \textbf{Next:}
    \State \quad \texttt{counter} $\gets$ \texttt{ite}(\texttt{reset}, $0$, \texttt{counter} $+ 1$)
    \State \quad \texttt{\_resetCount} $\gets$ \texttt{ite}(\texttt{\_resetCount} $< 1$, $1$, \texttt{\_resetCount})
    \end{algorithmic}
\end{algorithm}

\textbf{Step 0} The executor begins with the initial configuration. Step 0 starts with one path and no assumptions (path condition $\mathit{true}$). We set up the state variables: the BTOR2 model gives \texttt{counter} no explicit initial value, so we assign it a fresh timestamped symbol \texttt{counter\_t0} (16-bit). \texttt{\_resetCount} (1-bit) is initialized to $0$ as specified. At each step, the input \texttt{reset} is chosen nondeterministically and represented by a timestamped symbol (e.g., \texttt{reset\_t0} at step 0, \texttt{reset\_t1} at step 1). The system constraint $\mathit{implies}(\neg(\mathit{\_resetCount} \geq 1), \mathit{reset})$ has antecedent true (since $\mathit{\_resetCount} = 0$), so \texttt{reset} must hold. Thus the path condition includes \texttt{reset}. The table below shows the single path: \texttt{counter} $= \texttt{counter\_t0}$, \texttt{\_resetCount} $= 0$.

\begin{center}
\begin{tabular}{|c|l|c|c|}
\hline
\textbf{Path} & \textbf{Constraints} & \textbf{counter (16-bit)} & \textbf{\_resetCount (1-bit)} \\
\hline
1 & \texttt{reset} & \texttt{counter\_t0} & 0 \\
\hline
\end{tabular}
\end{center}

\textbf{Step 1} We take each path produced at step 0 and apply the transition function to it. Step 0 had one path, so we have one path to process. We introduce \texttt{reset\_t0} for the input at this step. The constraint forced \texttt{reset} to hold at step 0, so we are in the ``reset'' branch of the \texttt{ite}: \texttt{counter} becomes $0$ and \texttt{\_resetCount} becomes $1$. After the transition, $\mathit{\_resetCount} = 1$, so $\neg(\mathit{\_resetCount} \geq 1)$ is false and the system constraint is vacuously satisfied (simplifies to $\mathit{true}$). The path condition remains \texttt{reset} (or true). We still have one path: \texttt{counter} $= 0$, \texttt{\_resetCount} $= 1$.

\begin{center}
\begin{tabular}{|c|l|c|c|}
\hline
\textbf{Path} & \textbf{Constraints} & \textbf{counter (16-bit)} & \textbf{\_resetCount (1-bit)} \\
\hline
1 & $\mathit{true}$ & 0 & 1 \\
\hline
\end{tabular}
\end{center}

\textbf{Step 2} We take each path from step 1 and apply the transition. Step 1 had one path, so we start with one path. We introduce \texttt{reset\_t1} for the input at this step. The next-state expression for \texttt{counter} is \texttt{ite}(\texttt{reset}, $0$, \texttt{counter} $+ 1$). We cannot evaluate this concretely because \texttt{reset} $= \texttt{reset\_t1}$ is symbolic. We create two successor paths, one assuming \texttt{reset\_t1} $= \mathit{true}$, one assuming \texttt{reset\_t1} $= \mathit{false}$. \textbf{Path 1} (reset held): \texttt{reset\_t1} $= \mathit{true}$, so \texttt{counter} stays $0$ and \texttt{\_resetCount} stays $1$. Path condition: \texttt{reset\_t1}. \textbf{Path 2} (reset false): \texttt{reset\_t1} $= \mathit{false}$, so \texttt{counter} becomes $1$ and \texttt{\_resetCount} stays $1$. Path condition: $\neg$\texttt{reset\_t1}. We now have two paths, each inheriting from the single path at step 1 but branching on the symbolic input.

\begin{center}
\begin{tabular}{|c|l|c|c|}
\hline
\textbf{Path} & \textbf{Constraints} & \textbf{counter (16-bit)} & \textbf{\_resetCount (1-bit)} \\
\hline
1 & \texttt{reset\_t1} & 0 & 1 \\
2 & \texttt{not(reset\_t1)} & 1 & 1 \\
\hline
\end{tabular}
\end{center}

\textbf{Step 3} We take each of the two paths from step 2 and apply the transition. For each path, we introduce \texttt{reset\_t2} for the input at this step. Each path branches on \texttt{reset\_t2} (true or false), yielding four paths with no merging. \textbf{Path 1} continues from step 2 path 1 with \texttt{reset\_t2} $= \mathit{true}$: \texttt{counter} stays $0$. Path condition: \texttt{reset\_t1} $\land$ \texttt{reset\_t2}. \textbf{Path 2} continues from step 2 path 1 with \texttt{reset\_t2} $= \mathit{false}$: \texttt{counter} was $0$, so it becomes $1$. Path condition: \texttt{reset\_t1} $\land$ $\neg$\texttt{reset\_t2}. \textbf{Path 3} continues from step 2 path 2 with \texttt{reset\_t2} $= \mathit{true}$: \texttt{counter} was $1$, so it becomes $0$. Path condition: $\neg$\texttt{reset\_t1} $\land$ \texttt{reset\_t2}. \textbf{Path 4} continues from step 2 path 2 with \texttt{reset\_t2} $= \mathit{false}$: \texttt{counter} was $1$, so it becomes $2$. Path condition: $\neg$\texttt{reset\_t1} $\land$ $\neg$\texttt{reset\_t2}. The bad-state predicate is $\neg\mathit{reset} \land (\mathit{counter} > 1)$. On path 4, \texttt{reset\_t2} $= \mathit{false}$ (so $\neg\mathit{reset}$ holds) and \texttt{counter} $= 2 > 1$, so the bad state is satisfied. The executor reports that the system is unsafe: a concrete trace (e.g., \texttt{reset\_t0} $= \mathit{true}$, \texttt{reset\_t1} $= \mathit{false}$, \texttt{reset\_t2} $= \mathit{false}$) reaches the bad state at step 3.

\subsection{Initialization}

Initialization sets up the data structures that the symbolic executor will maintain throughout execution. Before describing the procedure itself, we first examine the two core types it operates on: the \texttt{SymbolicExecutor} struct, which holds all persistent state, and the \texttt{ExecutionPath} struct, which represents a single feasible branch.

\subsubsection{SymbolicExecutor Fields}

The \texttt{SymbolicExecutor} struct is the top-level object. It is constructed from a parsed BTOR2 transition system and owns all data that persists across steps:

\begin{center}
\begin{verbatim}
pub struct SymbolicExecutor {
    ts: TransitionSystem,
    current_step: usize,
    paths: Vec<ExecutionPath>,
    state_types: HashMap<ExprRef, Type>,
    input_types: HashMap<ExprRef, Type>,
    all_symbols: HashSet<ExprRef>,
    constraints: Vec<ExprRef>,
    bad_state: Option<(ExprRef, ExecutionPath)>,
}
\end{verbatim}
\end{center}

\noindent The fields serve the following roles:
\begin{itemize}
    \item \texttt{ts} — the parsed BTOR2 model, including the state variables, inputs, next-state expressions, constraints, and bad-state predicates.
    \item \texttt{current\_step} — the number of transitions that have been applied so far, used to generate unique timestamped names for new symbols.
    \item \texttt{paths} — the set of active symbolic execution paths. Each path represents one feasible branch of execution reached so far.
    \item \texttt{state\_types} / \texttt{input\_types} — maps from expression references to their BTOR2 types (bit-vector width or array type), consulted whenever a fresh symbol must be allocated with the correct type.
    \item \texttt{all\_symbols} — the universe of all symbolic variables that have been introduced. Every variable declared here is forwarded to the SMT solver before checking satisfiability.
    \item \texttt{constraints} — the system-level constraints copied from the transition system. These are asserted in every SMT query so that only inputs satisfying the BTOR2 \texttt{constraint} declarations are considered.
    \item \texttt{bad\_state} — set to \texttt{Some} the first time a bad-state predicate is found satisfiable on any path, pairing the violating expression with the witness path. Subsequent calls to \texttt{step} return immediately with \texttt{StepResult::BadStateReached} without modifying any other field.
\end{itemize}

Each active branch is stored as an \texttt{ExecutionPath}:

\begin{center}
\begin{verbatim}
pub struct ExecutionPath {
    pub state_translation: HashMap<ExprRef, ExprRef>,
    pub path_conditions: Vec<ExprRef>,
    pub input_translation: HashMap<ExprRef, ExprRef>,
    pub new_state_cache: HashMap<ExprRef, ExprRef>,
}
\end{verbatim}
\end{center}

\noindent \texttt{state\_translation} maps each state variable to its current symbolic value along this branch. \texttt{path\_conditions} is the list of branch constraints accumulated to reach this configuration; their conjunction is the path condition. \texttt{input\_translation} maps each input variable to the timestamped symbol allocated for the current step (e.g.\ \texttt{reset\_t0}). \texttt{new\_state\_cache} is a scratch map used during a step to hold freshly computed next-state values before they are committed to \texttt{state\_translation}.

\subsubsection{Initialization Procedure}

The \texttt{init} method creates the single starting path and populates the type maps:

\begin{center}
\begin{verbatim}
pub fn init(&mut self, ctx: &mut Context) {
    for state in &self.ts.states {
        self.state_types.insert(state.symbol, state.symbol.get_type(ctx));
    }
    for input in &self.ts.inputs {
        self.input_types.insert(*input, input.get_type(ctx));
    }

    let mut initial_path = ExecutionPath::new();

    for state in &self.ts.states {
        if let Some(init_expr) = state.init {
            initial_path.state_translation.insert(state.symbol, init_expr);
        } else {
            let name = ctx.get_symbol_name(state.symbol).unwrap_or("state");
            let t0_name = format!("{}_t0", name);
            let tpe = self.state_types[&state.symbol];
            let t0_sym = match tpe {
                Type::BV(width) => ctx.bv_symbol(&t0_name, width),
                Type::Array(arr_type) => ctx.array_symbol(
                    &t0_name, arr_type.index_width, arr_type.data_width),
            };
            initial_path.state_translation.insert(state.symbol, t0_sym);
            self.all_symbols.insert(t0_sym);
        }
    }

    self.constraints = self.ts.constraints.clone();
    self.paths.push(initial_path);
    self.current_step = 0;
}
\end{verbatim}
\end{center}

The procedure works in two phases. First, it records the type of every state variable and input by iterating over the transition system and inserting into \texttt{state\_types} and \texttt{input\_types}. These maps are consulted later whenever a fresh symbol of the correct width must be allocated.

Second, it builds the single initial \texttt{ExecutionPath}. For each state variable the BTOR2 model provides an explicit \texttt{init} expression (e.g.\ \texttt{\_resetCount} $\gets 0$), that concrete value is used directly. For state variables with no explicit initializer (e.g.\ \texttt{counter}), a fresh unconstrained symbol is created with the suffix \texttt{\_t0} and registered in \texttt{all\_symbols}. This symbol represents the unknown initial value and will be treated as a free variable by the SMT solver. Finally, the system constraints are copied from the transition system and the single initial path is pushed onto \texttt{paths}.

\subsection{Simplification}

The goal of simplification is to reduce expressions to forms that cannot be simplified any further. This process relies on a set of basic simplification rules that operate only on the surface structure of an expression. These rules are simple and locally applicable. For example, if both operands of an addition are integers, the expression can be simplified to their sum. Similarly, if the condition of an if expression evaluates to true, the entire expression simplifies to the true branch. However, these rules apply only when their conditions are directly satisfied at the top level of the expression. If an operand is itself a more complex expression (for example, an addition where one operand is symbolic), the rule does not apply. Simplification therefore proceeds by repeatedly applying these basic rules wherever they match. The process continues until no rule can be applied anymore, at which point the expression has reached a fixed point and is considered fully simplified.

To simplify expressions and expression references, we need to start by simplifying the inner most layer. This is implemented with a stack. Each child of an expression gets added to a stack and the last children added is popped and simplified. Table~\ref{fig:btor-simplify} traces this algorithm on the expression $\mathit{If}(\mathit{true}, \mathit{If}(\mathit{add}(0,1), 4, 5), -1)$: the first column is the step (number of pops), the second is the current result overall (the full expression with all completed simplifications applied so far), the third is the current simplification target (the expression just popped), and the fourth is the stack (top to bottom) after pushing that target's children, if any. The expression simplifies to $4$: $-1$, $4$, and $5$ do not simplify; $\mathit{add}(0,1)$ simplifies to $1$; $\mathit{If}(1, 4, 5)$ simplifies to $4$ (condition is true); $\mathit{If}(\mathit{true}, 4, -1)$ simplifies to $4$.

\subsection{Finding nested if-statements}

Using the idea for simplification, the same method can be used to traverse through nested if-statement. Start by implementing a stack which holds all the expressions, a stack which holds all the traversed paths, and a map which holds the position of each expression reference. For each expression, add each child to the mapping, and then explore each children. If any of the children are an ITE expression, we should simplify the path to either the true or false expression and add this to the path stack. Then, with the assumption that the ite is true or false, we can use simplification to simplify the expression and add it to the expression stack. Do this for each path as well and eventually we will have a list of paths which represent all feasible combinations of paths and, for each path, the new states. 

Consider the expression $\mathit{add}(\mathit{ite}(x, 1, 2),\; \mathit{ite}(y, 2, 3))$ where $x$ and $y$ are unconstrained symbolic booleans. There are two nested ITE sub-expressions, one inside each argument of $\mathit{add}$, producing four feasible execution paths. Figure~\ref{fig:nested-ite-tree} shows the resulting path-exploration tree.

\subsection{Pruning Redundant Branches}

Not every \textit{ite} expression necessarily results in a branch during symbolic execution. Consider the expression $ite(x>2, ite(x>1, 0, 1), 1)$: the condition of the inner \textit{ite} is already entailed by the outer condition, rendering one of its branches unreachable. To handle this precisely, we issue the following queries to the SMT solver:
\begin{enumerate}
    \item{$P\land c = \textit{SAT} \land P\land \lnot c = \textit{SAT}$}: The SMT solver says that both paths are feasible. In this case, we create two branching executions one with $P'=P\land c$ and one with $P'=P\land \lnot c$. 
    \item {$P\land c = \textit{SAT} \land P\land \lnot c = \textit{UNSAT}$}: The SMT solver says that the path such that $\lnot c$ is impossible. This means that given the information of $P$, $\lnot c$ is infeasible. As such, we do not need to add $\lnot c$ into the path, as the information is already recorded in the path. You can think of this as a node with one branch. It has no other choice so no branching executions are created. Consider $P=(x==10)\land (y==11), c=(x+y>12)$. There is no need to add $c$ to the execution path because the value is already included in $P$. 
    \item {$P\land c = \textit{UNSAT} \land P\land \lnot c = \textit{SAT}$}: She SMT solver says that the path such that $c$ is impossible. Similar to the previous case, we do not need to add $c$ onto the path as the information for deducing $\lnot c$ is already included in $P$. 
    \item {$P\land c = \textit{UNSAT} \land P\land \lnot c = \textit{UNSAT}$}: The result states that regardless of $c$ the execution is infeasible. This must mean that $P$ is infeasible, which means the constraints were infeasible. 
\end{enumerate}

\subsection{Path Merging}

The current implementation of symbolic execution with just one \textit{ite} expression will double in size with each step. Consider the following state: $x:=\textit{ite}(i>0,x+1, x-1)$. Given the constraint that $i$ is an input and that $i$ is either $1$ or $0$, there is exists two branches in each step. As such within $5$ steps, the number of symbolic execution paths will be $2^5=32$. 

To counter state explosion, we imploy is path merging. In the previous example, consider the branch that the input is first $0$ then $1$ versus first $1$ then $0$. Both symbolic paths result in the same system state. As a result, we can combine the two paths with an $\land$ to prevent state explosion.

Figure~\ref{fig:path-merging} illustrates the first two steps of this example ($x_0$ is the initial value of $x$). Without merging, the four paths at step~2 are tracked separately. With merging, the two paths that reach $x=x_0$ (one via $i_1{=}0,i_2{=}1$ and one via $i_1{=}1,i_2{=}0$) are combined, reducing the live path count.
